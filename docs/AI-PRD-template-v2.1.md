# AI 产品需求文档（AI PRD）通用框架 v2.1

> 模板修订：2.1（增加个人项目填写模式）。下方“文档信息”中的版本记录供实际项目使用。

> 适用于生成式 AI、RAG、Agent、推荐/预测/分类、语音/视觉和混合式 AI 产品。填写时保留全部核心章节；按能力启用专项模块。可按 §0.5 选择个人项目填写模式；不要虚构技术组件或尚不存在的商业决策。
>
> 本文件是**可复用的产品需求模板**，不是标准、法律意见或技术架构规范。方括号 `[...]` 是待填内容；表格示例值均须用项目证据替换。

## 0. 使用说明与适用性判定

### 0.1 填写原则

1. **先描述产品问题，再决定技术形式。** 写明现有流程和不使用 AI 的可行方案。
2. **核心章节 §1—§15 均保留。** 根据实际情况写“已验证 / 待验证 / 待定 / 暂缓 / 不适用”，并按 §0.2 给出依据或后续动作；核心决策不能仅靠标记跳过。
3. **专项模块按触发条件填写。** 一个产品可以同时启用多个模块；模块不是互斥的产品分类。
4. **产品要求与实现设计分开。** 主文说明用户行为、系统边界、输入输出、质量和约束；复杂 prompt、索引 schema、工具 JSON schema、基础设施方案链接到技术附件。
5. **发布条件与成功条件分开。** 离线验收决定是否允许发布；真实用户/业务结果决定发布后是否成功。
6. **来源、推导、约定分开。** 标注 `法规/合同义务`、`外部框架建议`、`本项目决策`，并注明适用条件与核实状态。

### 0.2 文档状态标记

| 标记 | 含义 | 填写要求 |
|---|---|---|
| 已验证 | 有可回溯证据或测试结果 | 附链接、版本或记录 |
| 待验证 | 本阶段必须考虑，但结论尚无证据 | 写清假设、验证方法、判断标准、负责人和时间；关键假设标明阻塞节点 |
| 待定 | 已识别决策或外部确认事项，尚无结论 | 写可选方案、阻塞节点、决策人和期限 |
| 暂缓 | 可能适用，但当前阶段无需决策 | 写阶段理由与重新评估的时间或触发条件；不可暂缓当前安全或发布门槛 |
| 不适用 | 当前产品能力或实际用途不触发该项 | 写事实理由；若未来能力变化会触发，写重新评估条件 |

> “暂缓”表示阶段选择，“不适用”表示范围判断；“待验证”表示证据缺口，可以与章节的适用性并存。“已实现”和“已验证”是两个不同状态。实现完成不代表达到质量门槛。

### 0.4 每节的填写契约

每节按以下口径填写：**适用性 → 必须回答的问题 → 最低交付物 → 证据或假设 → 验收/决策依据 → 负责人**。模板提供字段，项目团队可以增加细节，但不以“写满字数”作为完成标准。

### 0.5 个人项目／原型验证阶段填写模式（可选）

**启用条件：**由个人或小团队负责、当前目标是验证一个具体用户问题和最小可行方案，尚未承诺规模化运营。填写文档信息中的“项目阶段”，并注明本轮决策是“继续探索 / 开始开发 / 邀请试用 / 对外发布”中的哪一项。项目进入公开试用、商业化或高影响用途时，按实际范围补充相应内容并重新评审。

**仍需写清的最小闭环：**§1 的目标与本轮决策；§2—§3 的用户问题、现有替代方式和至少一个任务场景；§5—§6 与 §11 的本期能力、流程和 P0 验收；§7 的实际数据流；§8—§10 的成功判断、任务质量与可执行评测；§12—§13 的用户纠错、失败行为和关键风险；§15 的待验证假设与下一步决策。§4、§14 保留，但按下表调整深度。涉及真实用户、敏感数据、外部动作或公开发布时，按实际风险提高验证深度。

| 模板位置 | 个人项目阶段的最低填写方式 | 可暂缓的内容与重评触发 |
|---|---|---|
| §4 战略关系 | 写个人项目目标：验证用户价值、学习某项能力、形成可展示案例等；说明现有替代工具的缺口 | 组织战略、市场规模；准备商业推广或争取组织资源时重评 |
| §4 商业模式 | 若当前不收费，写“本阶段不验证商业化”，并说明是否存在真实成本与预算上限 | 收费、获客和收入预测；决定收费或规模化运营时重评 |
| §5 计划与角色 | 写最近一次实验或原型里程碑、P0 范围和实际负责人；一人可兼任多种角色 | 多角色排期和远期版本计划；协作人数或交付承诺增加时重评 |
| §8—§10 成效与评测 | 设一个可观察的任务结果、可比较的基线、少量有代表性的场景及关键失败用例；写样本局限，保留独立验收的原则 | 大规模 A/B 和复杂统计设计；样本量与发布范围扩大时深化 |
| §14 运维 | 写 API/运行预算上限、基本故障处理、停用方式；若仅在本机验证，说明数据去向 | 容量规划、SLA/SLO、多环境运维；面向外部用户持续提供服务时重评 |
| §15 评审 | 一人可自己记录“证据—结论—下一步”；关键风险可邀请试用者或有相关经验者复核 | 多部门签署；项目进入组织协作、合同交付或公开发布时重评 |

**状态示例：**没有知识库 → “B 不适用：产品不检索外部资料”；尚未收费 → “§4 商业模式暂缓：试点完成后再决定”；学习效果尚无用户证据 → “§8 待验证：先完成一轮任务对照测试”。不能把尚未证实的用户价值、AI 质量、必要的数据处理或关键安全风险写成“不适用”。

**个人项目的阶段出口：**在 §15 记录一轮试用或评测后的证据、样本限制、P0 阻断项，以及“继续 / 缩小范围 / 调整 / 停止”的决定。原型验证通过不自动等于可以公开发布；公开发布时仍需满足 §10 的相应发布门槛。

## 附录 J. 完整性与可执行性自检

- [ ] 每个启用的模块都能指向一个真实用户场景或风险；不适用项有理由。
- [ ] 产品问题、替代基线、AI 增量和成功指标串得起来。
- [ ] 每个 P0 需求有负责人、依赖、验收与目标版本。
- [ ] 输入、输出、数据流、权限、副作用、人工确认和恢复动作已定义。
- [ ] 评测定义允许不同团队复现同一判断；高风险场景不会被总体平均数掩盖。
- [ ] 上线前质量门槛与上线后成效指标分开。
- [ ] 来源、未验证假设、项目约定和具体法律义务没有混写。
- [ ] 发布失败、运行故障、错误决策、申诉和停用均有责任人。
