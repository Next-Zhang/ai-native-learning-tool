# AI 产品需求文档（AI PRD）通用框架 v2.2

> **模板版本**：2.2 —— 在 2.1 基础上补齐**九项必备内容**（见 §0.2），并精简填写说明。v2.1 被本版取代。
> **适用**：生成式 AI、RAG、Agent、推荐／预测／分类、语音／视觉及混合式 AI 产品。
> **这是什么**：可复用的产品需求模板，不是标准、法律意见或架构规范。`[方括号]` 为待填内容；示例值必须替换为项目证据。
> **写作标准**：**清晰、简洁、易理解**。一张表能说清就不写三段话。
> **怎么读**：§0 是模板使用说明（填写完的实际 PRD 可以去掉）。评审时**先看 §0.2 的九项对照表**，再按 §1 → §4 → §6.5 → §10 快速判断是否立得住；其余章节用于查证细节（模型选型、prompt 治理、质量控制链与原型各有一章）。

## 0. 怎么用这份模板

### 0.1 五条写作纪律

1. **先写产品问题，再写技术形式。** 写清现有流程和不使用 AI 的替代方案。
2. **九项必备内容缺一不可。** 对照 §0.2；某项确实不适用，写明事实理由与重评触发条件，不能空着。
3. **产品要求与技术设计分开。** 主文写用户行为、边界、输入输出、质量与约束；prompt、schema、架构细节放 §17 与技术附件并给链接。
4. **发布条件与成功条件分开。** 离线验收决定能不能发；真实用户结果决定发出去是否成功。
5. **事实、假设、项目决定分开。** 标注 `法规/合同义务`、`外部框架建议`、`本项目决策`，并注明证据与核实状态。

### 0.3 状态标记（五档）

| 标记 | 含义 | 填写要求 |
|---|---|---|
| 已验证 | 有可回溯证据或测试结果 | 附链接、版本或记录 |
| 待验证 | 本阶段必须考虑，但尚无证据 | 写假设、验证方法、判断标准、负责人、阻塞节点 |
| 待定 | 已识别的决策或外部确认事项，尚无结论 | 写可选方案、阻塞节点、决策人、期限 |
| 暂缓 | 可能适用，但当前阶段无需决策 | 写阶段理由与重评触发；**不可暂缓安全或发布门槛** |
| 不适用 | 当前能力或实际用途不触发该项 | 写事实理由；能力变化会触发时写重评条件 |

> "暂缓"是阶段选择，"不适用"是范围判断，"待验证"是证据缺口，三者可并存。**"已实现" ≠ "已验证"**：实现完成不代表达到质量门槛。

### 0.5 个人项目／原型验证阶段模式（可选）

**启用条件**：个人或小团队负责、当前目标是验证一个具体用户问题和最小可行方案、尚未承诺规模化。填写文档信息中的"项目阶段"，并注明本轮决策是"继续探索／开始开发／邀请试用／对外发布"中的哪一项。进入公开试用、商业化或高影响用途时，按实际范围补充内容并重新评审。

**仍需写清的最小闭环**：§2 的问题与 LLM 必要性；§4.1／§4.2 两类目标；§5 本期范围与迭代计划；§6.5 三类需求；§10 可执行评测；§16 模型选型依据；§17 prompt 清单与变更门禁；§18 质量控制链；§19 原型与边界；§15 待验证假设与下一步决策。**§4.3、§5、§8—§10、§14、§15 按下表调整深度。**

| 模板位置 | 个人项目阶段的最低填写方式 | 可暂缓的内容与重评触发 |
|---|---|---|
| §4.3 机会、定位与约束 | 写个人目标（验证用户价值、形成可展示作品等）；不收费就写"本阶段不验证商业化"并给出成本与预算上限 | 组织战略、市场规模、收入预测；决定收费或争取组织资源时重评 |
| §5 范围与迭代计划 | 写最近一个里程碑、P0 范围与实际负责人；一人可兼任多角色 | 多角色排期与远期版本；协作人数或交付承诺增加时重评 |
| §8—§10 成效与评测 | 设一个可观察任务结果、可比较基线、少量代表性场景与关键失败用例；**写样本局限**；保留独立验收集原则 | 大规模 A/B 与复杂统计；样本量与发布范围扩大时深化 |
| §14 运维 | 写 API/运行预算上限、基本故障处理、停用方式与数据去向 | 容量规划、SLA/SLO、多环境运维；对外持续服务时重评 |
| §15 评审 | 一人记录"证据→结论→下一步"；关键风险邀请试用者或有经验者复核 | 多部门签署；进入组织协作、合同交付或公开发布时重评 |

**红线**：不得把尚未证实的**用户价值、AI 质量、数据处理、关键安全风险**写成"不适用"。**阶段出口**：在 §15 记录一轮试用或评测后的证据、样本限制、阻塞项，以及"继续／缩小范围／调整／停止"的决定；原型通过不等于可以公开发布。

### 0.6 每节的填写契约

每节统一按：**适用性 → 必答问题／表 → 最低交付物 → 证据或假设 → 验收／决策依据 → 负责人**。模板给字段，团队可加细节；**"写满字数"不是完成标准**。

## 附录 J. 完整性与可执行性自检

**九项必备内容**

- [ ] **产品价值**：问题有证据，非 AI 基线与"为什么用 LLM"写清（§2）。
- [ ] **目标定义**：业务目标与模型目标分开，且模型目标可追溯到业务目标（§4）。
- [ ] **需求与方案**：核心功能、性能要求、安全需求各有清单与验收方式（§6.5）。
- [ ] **流程梳理**：业务流程与系统流程分开，且失败分支有恢复动作（§6.1、§6.2）。
- [ ] **模型选型**：先定标准后比候选，有实测依据、降级方案与重评触发（§16）。
- [ ] **Prompt**：有清单与版本记录，变更经评测验证，可回滚（§17）。
- [ ] **评测体系**：评测集、判分标准、执行流程、发布门槛齐全且可复现（§10）。
- [ ] **效果与稳定性**：从模型输出到用户可见结果的每层都有手段、兜底与可观测（§18）。
- [ ] **原型与边界**：关键状态有原型、边界有清单、迭代有退出条件（§19、§5.3）。

**其余检查**

- [ ] 每个启用的模块都指向一个真实用户场景或风险；不适用项有理由与重评触发。
- [ ] 用户、受影响者与场景有证据或明确的验证计划（§3）。
- [ ] 数据流、权限与第三方依赖有清单和核实状态（§7）。
- [ ] 追溯矩阵无断链：每个 R-xx 都能串到 FR-xx、模型目标、M-xx 与 T-xx（§11）。
- [ ] 每个 P0 需求有负责人、依赖、验收与目标版本。
- [ ] 四个交互时机有产品行为定义与验证方式（§12）。
- [ ] 高风险失败有检测手段、恢复动作与责任人（§13）。
- [ ] 上线前质量门槛与上线后成效指标分开。
- [ ] 义务判断与待定决策都有责任人、期限和核实状态（§15）。
- [ ] 高风险场景不会被总体平均数掩盖；无法度量的风险已记录。
- [ ] 事实、假设、项目约定与法律义务没有混写。
- [ ] 发布失败、运行故障、错误决策、申诉和停用均有责任人。
- [ ] 技术细节有可访问的设计链接，PRD 主文能独立完成产品评审。
- [ ] 全文没有靠篇幅撑起来的段落：**能用表格或一句话说清的，就不写三段**。
