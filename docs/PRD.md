## 一页速览

**产品一句话**：面向泛自学者的**「验收式学习」教练 Agent**——它先测你的真实水平，再排一份按你时间滚动的 7 天计划，每天给你一个任务，**你交产出、它结构化验收**，并把结果写进你的能力画像，用于调整下一轮。

**要解决的问题**：自学者用通用大模型或课程平台自学时，① 计划是通用模板，不随个人水平/时间滚动；② 学完**无人验收**，无法确认是否真的掌握；③ 复习与遗忘无安排。→ 证据为**待验证**（见 1.2）。

**需求 → 方案 → 验收 总表**（详细展开见 1.3 / 2.2 / 第三幕）：

| 需求（用户要什么） | 方案（系统怎么满足） | 验收（怎么证明） | 本期 |
|---|---|---|---|
| **UR-01** 要按我水平/时间/期限定制、且能随进展滚动的计划，不要通用模板 | **S-01** 状态机 planning：窗口 = min(7, 期限)，优先覆盖薄弱点；**生成后必须我确认**才执行 | T-01 / T-03；计划可执行性抽样 | ✅ 已实现 |
| **UR-02** 要确认"我真的会了"，不接受"我懂了" | **S-01** evaluation：要求可检验证据 → 完成度三档 + 错误类型 + 下一步；无产出即判未完成 | M-01；T-04 | ✅ 已实现 |
| **UR-03** 要它记住我的水平和薄弱点，并据此调整后续 | 画像由**代码聚合**（非模型给分）+ 薄弱点阈值 <0.6 → 回灌下一轮计划 | 聚合单测；M-01 分层 | ✅ 已实现 |
| **UR-04** 要能理解它为什么这样判，并在我不同意时纠正 | 给出完成度 + 错误类型 + 判定理由 + 反馈；可反驳、可重做当前任务 | 2.9 理解测试；T-05 | ✅ 已实现 |
| **UR-05** 能力不够或没资料时要诚实说，不能编造 | 无自建知识库 → **S-04** 联网检索标来源；检索失败声明"未找到"；接口失败**保持当前阶段不误推进** | M-05；T-06 | 🔸 部分 |
| **UR-06** 我信息没给全时，要先问我关键问题，别瞎猜 | **S-01** 目标澄清阶段：一次只问 1~2 个关键问题；四字段齐才放行 | T-02 | ✅ 已实现 |
| **UR-07** 重建计划/改目标/删历史这些大事必须先问我 | **S-08** HITL 确认门：代码层 `require_human_confirmation(action_id)`，**拒绝/超时均不执行** | T-10 | ⬜ 待实现（现仅提示词层） |
| **UR-08** 我要能控制和删除自己的数据 | `/reset` 清历史、`/reset all` 完全重置；`coach/storage/reset.py` 带备份 | 单测 | ✅ 已实现 |
| **UR-09** 同一个产品要能覆盖多个领域（编程 / 心理学） | **S-02** 领域配置（知识点/计划模板/出题策略/rubric）+ **S-05** 双领域闭环 | T-01 分领域 | ⬜ 待实现 |
| **UR-10** 学习要能跨多天持续，并让我随时知道进度和下一步 | **S-01** 计划游标 + 进度展示 + **S-09** 记忆窗口（阶段隔离 + 8 条） | T-01；M-03 | 🔸 部分 |
| **UR-11** 想通过"讲给别人听"来巩固（后续） | **S-11** teaching 教中学环节 | 后续同链对比 | ⬜ 后续版本 |

**方案总览一句话**：**固定流程（workflow）+ 模型辅助**——阶段转换由**代码守卫**决定（`coach/domain/stages.py` 是唯一来源，一次只推一档），LLM 只在阶段内做内容生成与结构化判定；每阶段单次 `deepseek-chat` JSON 调用（`temperature=0`）。依据 Anthropic《Building effective agents》的 workflow/agent 区分。

**本期范围**：让一条闭环在**两个领域**都真正跑通并可评测（见 2.10）。
**本轮决策**：**开始开发**；决策人=本人；支撑证据=**73 个测试（7 套）通过**、真实会话 `plan_progress.completed=['1-1']`。
**最大未验证假设**："验收式学习"相比"通用大模型 + 自排计划"能带来**可观察的学习效果增量**（**待验证**，见 1.5 与 3.7）。

**行动清单**：见文末《结论与行动清单》（A-01…A-09，含负责人、依赖与截止）。**发布阻断项** = S-07（指标采集）与 S-08（HITL 代码强制）。

# 第一幕 · 需求

## 1.1 执行摘要与决策请求

**（终局愿景，仅作定位锚点，待验证）** 面向泛自学者的**多领域学习教练 Agent**：定制计划 + 结构化验收 + 记录画像 + 滚动改进；领域可插拔、可联网、可评测。**本表不展开为远期规格**；MVP 是朝它推进的第一个切片。

**（本轮）** 为泛自学者在多日滚动学习场景提供「验收式学习」教练 Agent，解决"计划不滚动、学完无人验收、复习无安排"的问题，预期使 **7 天滚动计划完成率**从**待测基线**提升到**待定目标**（见 3.1）。

- **AI 执行**：澄清、测评出题与判分、计划生成、任务下发、结构化验收、画像更新、联网检索。
- **人负责**：澄清目标、**确认计划**、提交任务产出、确认重大变更、在 AI 出错时纠正与接管。
- **本次请求决策**：**开始开发**（继续实现 MVP）。证据：73 测试通过、闭环已跑通。

## 1.2 用户、场景与问题

**主要用户**：泛自学者（如"学 Python 数据分析""入门心理学"）。**无真实用户访谈样本** → 相关主张标**待验证**。

| 项目 | 内容 |
|---|---|
| 目标用户在何时遇到什么问题 | 多日自主学习中：① 计划是通用模板，不随水平/可用时间滚动；② 学完**无人验收**；③ 复习与遗忘无安排 |
| 当前如何完成任务 | 通用大模型问答；或课程/教程平台 + 自己手工排计划、自己做题 |
| 问题的可观察证据 | **待验证**（无访谈/日志）。已有起点：自用会话记录；一手痛点"记忆有点杂乱，每轮读取全量历史"（已纳入 UR-10/S-09）。样本与日期**待补** |
| 影响 | 计划不可执行 → 放弃；无验收 → 假掌握；无复习 → 遗忘。频率与严重度**待验证** |
| 非 AI 基线 | 规则模板计划 + 人工测验/教材练习 + 日历提醒：成本低，但**不随水平调整、无结构化验收、不记画像** |
| AI 的预期增量 | 定制计划、自动出题判分、结构化验收定位薄弱点、基于画像滚动调整。**代价**：多轮调用带来成本/延迟线性增长与误差累积（见 3.4） |

**关键场景（已跑通，已验证）**：
`用户输入目标` → `目标澄清` → `能力测评` → `生成 7 天滚动计划` → `用户确认` → `每日任务` → `用户提交产出` → `结构化验收` → `画像更新` → 滚动下一轮。
证据：真实会话 `plan_progress.completed=['1-1']`。

**边界场景**：模糊输入、中途改目标、检索工具不可用、接口超时/限流（见 2.3、3.4）。

## 1.4 机会、定位与约束

## 1.5 需求验证计划（最小验证实验与基线）

> **目的**：UR-01…UR-11 目前**全部缺少用户证据**。本计划用最小成本尽快拿到定性+定量证据，据此决定**是否继续扩展 workflow**。

| # | 步骤 | 参与者 | 方法 | 成功标准 | 产出 |
|---|---|---|---|---|---|
| ① | **自用 7 天** | 作者 | 选一个陌生领域（如心理学入门），完整跑一个 7 天窗口 | 记录完成率、卡点、计划可执行性 | **3.1 基线** |
| ② | **每日微反馈**（与①②并行） | 作者 / 试用者 | 每天结束后 **10–15 分钟**：记一条"今天卡在哪 / 哪个任务不可执行 / 哪个判定我不认同" | 7 天内每天有一条可归类的记录 | 卡点清单（按 UR 归类） |
| ③ | **首日结构化访谈** | 作者 / 试用者 | **15 分钟**：进入前的期望、对"验收"的理解、是否愿意每天提交产出 | 能确认/推翻 UR-02、UR-10 的动机 | 访谈记录 |
| ④ | **末日结构化访谈** | 作者 / 试用者 | **15 分钟**：完成率自评、判定是否可信、是否愿意继续用 | 能判断"验收式学习"是否被真实需要 | 访谈记录 |
| ⑤ | **小样本外部验证** | 3 位自学者 | 各跑 3–7 天，重复 ②③④ | 能独立完成闭环；能复述判定理由 | UR-01~UR-10 的真实性证据 |

**样本局限（必须随结论一起报告）**：样本为熟人、非随机、**无对照组**，结论不可外推为普遍效果。
**决策依据**：若 7 天完成率相对基线的增量未达**待定门槛** → 先**简化 workflow / 收窄领域**，而非叠加复杂度。
**未验证前不得做的事**：不得据"机制已实现"推断"用户需要它"；不得把 UR 状态从**待验证**改为**已验证**而没有上述证据。

# 第二幕 · 方案

## 2.1 方案总览与架构定性

**核心机制**：一个由**代码守卫**驱动的状态机，把"学习"拆成可验收的步骤。

```
目标澄清 → 能力测评 → 学习计划(7天+用户确认) → 每日任务 → 提交 → 结果验收 → 画像更新
                                                                      └──────→ 回到每日任务
```

**分工（一句话）**：LLM 在每个阶段**内部**负责内容生成与判定；**代码决定是否推进**。

- **架构定性**：**固定流程（workflow）+ 模型辅助**。依据 Anthropic《Building effective agents》对 workflow（预定义代码路径编排）与 agent（模型动态决定自身流程与工具）的区分。
- **为什么这样定性**：① 步骤可预测；② "错误推进"的代价需要**硬约束**，不能交给模型自由裁量。
- **转换规则**：集中在 `coach/domain/stages.py` 的守卫中，**一次只推一档**，失败则保持原阶段。
- **最小可行方案**：规则状态机 + 每阶段**单次** JSON 模式模型调用（`temperature=0`）。
- **升级触发条件**：仅当阶段内需要多步工具链（如"检索→核对→出题"）时，才评估混合编排；且**必须**设最大步数与停止条件。
- **核心张力（重要）**：**架构上"五脏俱全"、运行时"按需触发"**——**不是每轮全链路调用**。每步 LLM 调用必须能说明可测收益，否则合并或删除，以对抗 workflow 膨胀带来的成本与误差累积。

**产品边界：**
- **能读**：本机 `data/user_state.json`、终端输入。

## 2.8 评分与决策机制（模块 E）

| 项目 | 内容 |
|---|---|
| 预测目标与时间窗 | ① 逐题判定 mastered/partial/missing；② 逐次验收 completed/partial/not_completed；③ 由其聚合的知识点**掌握度**与**薄弱点排序**（阈值 <0.6）。窗口=当前 7 天 |
