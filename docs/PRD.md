# AI Native Learning Tool 产品需求文档（PRD）

> **结构说明**：本文按「**需求 → 方案 → 验收**」三幕组织，让人能先读懂产品逻辑，再查细节。
>
> - **第一幕 需求**：为谁、解决什么问题、**要满足哪些需求（UR）**。
> - **第二幕 方案**：每条需求**用什么机制满足（S）**、系统边界、数据与交互。
> - **第三幕 验收**：**怎么证明满足了**（指标、评测、门槛、风险、合规）。
> - 与 v2.1 框架 §1–§15 的对照见 **附录 A**（框架合规性可追溯）；条件模块 A/C/D/E 融入第二幕，模块 H 见附录 B，B/F/G/I 见附录 C。
>
> **状态标记**：五档 **已验证 / 待验证 / 待定 / 暂缓 / 不适用**；实现状态另标 **✅已实现 / 🔸部分 / ⬜待实现**（两者不混用）。
> **项目模式**：个人项目模式（v2.1 §0.5）——由个人负责、验证具体用户问题与最小可行方案、尚未承诺规模化。**第一版以 MVP 为核心对象**；终局愿景仅作定位锚点。

### 术语与缩写（首次出现处也已就地说明）

| 术语 | 含义 |
|---|---|

| **HITL**（Human-in-the-Loop） | 人在回路：关键动作需人确认。本项目指不可逆动作（重建计划/改目标/删历史/标记已掌握）必须经用户确认（S-08） |
| **DeepSeek** | 本项目使用的第三方大模型服务商（`api.deepseek.com`）；本期只用 `deepseek-chat` 一个模型 |
| **LLM** | 大语言模型 |
| **workflow / agent** | Anthropic 的区分：workflow=由预定义代码路径编排；agent=模型动态决定自身流程。本项目为 **workflow + 模型辅助** |
| **UR / S** | UR=用户需求（要什么）；S=方案要素（怎么满足）。两者由 2.2 的映射表连接 |
| **rubric** | 评分量规：事先定义的判分维度与标准（本项目心理学的三层 rubric） |
| **JSONL / CSV** | 指标采集与导出的本机格式（S-07） |
| **P95** | 95 分位延迟 |
| **MVP** | 最小可行产品：能交付最小真实价值、供真实用户使用并迭代的第一个版本（≠ 原型） |
| **Go/No-go** | 发布决策结论（发布 / 不发布） |
| **SLA / SLO** | 服务等级协议/目标；个人项目本机阶段**暂缓** |
| **碎片化学习** | 用户只有 10–30 分钟的不连续时段（通勤 / 午休 / 睡前）。本项目的基本时间单位是**单次可用时长**，不是"每天总量" |
| **`session_minutes` / `sessions_per_week`** | 时间预算字段：单次可用时长 + 每周大约几次（**替代旧的 `daily_minutes`**） |
| **验收档位 L1 / L2 / L3** | 按时间预算分档的验收强度：**L1 复述/解释 · L2 应用 · L3 独立产出**。**档位由代码按 `session_minutes` 或用户显式选择决定，模型不得自行降档** |
| **例外转移** | 用户主动改变路径的**已登记**合法路径（换任务 / 缩短本次 / 结束窗口 / 跳过测评 / 换目标），而不是让模型自由发挥 |
| **趣味化反馈** | 提升学习趣味性的机制（连续天数、里程碑等）。**只允许作用于反馈层，不得影响验收结论与画像（I-9）** |

## 一页速览

**产品一句话**：面向**用碎片化时间快速理解与学习**的人（通勤 / 午休 / 睡前，一次 10–30 分钟）的**「验收式学习」教练 Agent**——你说想学什么、每次能给多少时间，它给你**一小块能在这一次内完成并交付**的任务；你交一个**小产出**，它按你的时间预算给出**相应强度**的验收（L1 复述/解释 → L3 独立产出），并把结果记进能力画像，**下次直接接上**。

**要解决的问题**：想用碎片时间学点东西的人，在现有工具之间拿不到「**可完成 + 被验收 + 能接续**」的闭环——① 通用大模型能答，但**不把碎片时间变成可完成的小任务**，也不验收、不记进度；② 短视频 / 知识付费是**被动消费**，看完即忘、无法确认是否理解；③ 课程平台周期长、任务大，**碎片时间推不动**。→ 证据为**待验证**（见 1.2）。

**需求 → 方案 → 验收 总表**（详细展开见 1.3 / 2.2 / 第三幕）：

| 需求（用户要什么） | 方案（系统怎么满足） | 验收（怎么证明） | 本期 |
|---|---|---|---|
| **UR-01** 我只有碎片时间（一次 10–30 分钟），要能在**一次内**完成一个学习单元 | **S-12 双层计划**：长期路线图（目标→里程碑）+ 短期执行窗口；**单位 = 次**；任务时长 ≤ `session_minutes`；窗口长度自适应 | T-01 单次可完成性抽样 | ⬜ 待实现 |
| **UR-02** 我要**快速确认自己理解了**，不要重作业 | **S-13** 分级验收 L1/L2/L3（按 `session_minutes` + **累积证据**定档；**模型不得降档**） | M-01 **按档分层** | ⬜ 待实现 |
| **UR-03** 要知道它凭什么这么判，不同意时能纠正 | 完成度 + 错误类型 + 理由 + 反馈；可反驳、可重做当前任务 | 2.9 理解测试；T-05 | ✅ 已实现 |

## 1.1 执行摘要与决策请求

## 1.2 用户、场景与问题

**主要用户**：**利用碎片化时间（一次 10–30 分钟）进行技能或知识快速理解与学习的人**。特征：① 时间碎片化、频率不固定；② 目标周期短（"这周搞懂 X"而非"三个月精通"）；③ **要自由度**（不接受被长期计划绑定）；④ **要低决策成本**（任务制定与执行一步到位）。**无真实用户访谈样本** → 相关主张标**待验证**。

| 项目 | 内容 |

| AI 的预期增量 | 按单次时长**切分可完成的小任务** + **分档验收**（L1/L2/L3）+ 画像累积与**跨会话接续** + 可选联网核实。**代价**：多轮调用带来成本/延迟线性增长与误差累积（见 3.4） |

证据：真实会话 `plan_progress.completed=['1-1','2-1','3-1']`（三次真实 API 会话累计）。

**边界场景**：模糊输入、中途换任务/换目标、**只想学一次**、**自带计划**、检索工具不可用、接口超时/限流（见 2.3、3.4）。

# 第二幕 · 方案

## 2.1 方案总览与架构定性

**核心机制**：一个由**代码守卫**驱动的状态机，把"学习"拆成可验收的步骤。

```
目标澄清 → 能力测评 → 学习计划(≤3天+用户确认) → 每日任务 → 提交 → 结果验收 → 画像更新
                                                                      └──────→ 回到每日任务
```

**分工（一句话）**：LLM 在每个阶段**内部**负责内容生成与判定；**代码决定是否推进**。

- **架构定性**：**可替换编排策略 —— 当前实现为「阶段×能力矩阵」（workflow）**，未来可升级为 hybrid（模型在允许集内提议步骤，代码校验）。依据 Anthropic《Building effective agents》对 workflow 与 agent 的区分。**正式决策见 [`docs/architecture.md`](architecture.md)**。
- **为什么这样定性**：① 步骤可预测；② "错误推进"的代价需要**硬约束**，不能交给模型自由裁量；③ **验收与授权不可让渡**——它们与"碎片化/灵活性"并不冲突，冲突只在"选步骤"这一层（由矩阵/提议策略决定）。
- **转换规则**：集中在 `coach/domain/stages.py` 的守卫中，**一次只推一档**，失败则保持原阶段。
- **最小可行方案**：规则状态机 + 每阶段**单次** JSON 模式模型调用（`temperature=0`）。
- **升级触发条件**：① 阶段内需要多步工具链（"检索→核对→出题"）；② **固定路径覆盖不足被实测证实**（用户意图频繁落在矩阵外）。升级时**必须**设最大步数与停止条件，并保持"提议须过守卫与授权门"。
- **核心张力（重要）**：**架构上"五脏俱全"、运行时"按需触发"**——**不是每轮全链路调用**。每步 LLM 调用必须能说明可测收益，否则合并或删除，以对抗 workflow 膨胀带来的成本与误差累积。**碎片化用户耐心更少，这条护栏更严。**

> **架构依据（正式决策）**：编排范式、能力扩展机制、自主权模型与感知契约的决议，以及**不得违反的不变量**，见 [`docs/architecture.md`](architecture.md)。其中 I-2 / I-3 直接来自 X-16 / X-17 两个实测缺陷。

## 2.3 核心流程与系统边界

| 阶段 | 用户动作/输入 | AI 的任务 | 规则/代码的任务 | 输出/状态 | 失败与恢复 |
|---|---|---|---|---|---|
| 目标澄清 | 说出学习需求 | 一次问 1~2 个关键问题 | `extract_profile` + `merge_profile`（空值不覆盖）；守卫 `profile_complete` | state 四字段 | 抽取失败 → 跳过画像，继续对话 |
| 能力测评 | 逐题作答 | 出 3~5 题（一次一题）；逐题判 mastered/partial/missing | `ensure_plan` 出大纲+兜底；`finalize` 纯代码聚合 | `skill_profile`/`weak_points` | 出题失败 → 兜底大纲；判分失败 → 保守记 missing |
| 学习计划 | 先看路线图，再逐窗口执行 | **生成长期路线图**（目标→里程碑）并请确认；确认后**下发一个执行窗口**（默认 = 一个里程碑所需的次数） | `derive_roadmap` / `derive_window`；守卫 `plan_confirmed`（路线图级） | `roadmap`/`current_window` | 生成失败 → 兜底计划；确认判定失败 → **保持等待** |
| 每日任务 | 学习并提交产出 | 每次只给 1 个任务；引导提交 | `build_today_task` 按游标取；`detect_submission` 判提交；守卫 `pending_submission` | `today_task`/`pending_submission` | 判定失败 → 保持 learning（**绝不把提问当提交**） |
| 结果验收 | 提交证据 | 按完成标准判定 | `evaluate` + `EvaluationResult` 一致性守卫 | `latest_result` | 判定失败 → 保持 evaluation |
| 画像更新 | 确认重大变更 | 反馈状态与下一步 | `apply_update` 纯代码算画像，按 pass/retry 决定推进或重做；守卫 `latest_result_applied` | 画像/游标 | 未通过 → 保留当前任务重做 |
| 复习 review / 已完成 completed | — | — | 仅定义提示词，**无自动进入与调度** | — | ⬜ 待实现 |

**计划模型（双层，v0.11 新增 · S-12）**

碎片化定位下，**"天"不是正确的计划单位**——用户可能一天学 3 次，也可能 3 天学 1 次。因此计划分两层，**单位是"次（session）"**：

| 层 | 名称 | 粒度 | 滚动 |
|---|---|---|---|
| **长期** | **路线图 `roadmap`** | 目标 → **里程碑**（覆盖整个目标周期） | **不滚动**；仅里程碑达成 / 目标变更时更新 |
| **短期** | **执行窗口 `current_window`** | **一次一个可完成单元** | **滚动**；窗口结束后按实际进度生成下一窗口 |

**窗口长度按需自适应（不再固定 3/7 天）**：

| 条件 | 窗口长度 |
|---|---|
| 有期限 + 每周次数 | 由里程碑与剩余可用时间推导 |
| 无期限、按里程碑 | = 该里程碑 `sessions_est`（默认 3–5 次） |
| **只想学一次** | **1 次**（无路线图） |
| 整块时间用户（`session_minutes ≥ 45`） | `unit` 切回 **`day`** —— 旧的 7 天窗口模型仍然可用 |
| **用户自带计划** | 按用户的阶段结构对齐里程碑（S-16 / I-7） |

- **`unit ∈ {session, day}` 由时间预算决定**：一套模型同时覆盖碎片化与整块时间，**旧资产不废弃**。
- **"滚动" = 重估，不只是换下一批**：若 M1 估 5 次、实际用 8 次，则后续里程碑估计**上调**、窗口长度随之调整。
- **确认门（避免频繁打断）**：路线图首次**必须**确认；同里程碑内的窗口滚动**不打扰**（只提示"下一窗口：M2 · 5 次"）；**跨里程碑需确认**；**改目标 = `danger`**（I-4）。

**产品边界：**

- **能读**：本机 `data/user_state.json`、终端输入。
- **能写**：本机 `data/user_state.json`、`data/backups/`（保留最近 5 份）。
- **不能**：任何外部写动作（发消息/改外部系统/支付）；无多用户与账号；除 LLM API 调用外无网络写操作。
- **外部系统**：DeepSeek API（`https://api.deepseek.com`）；联网检索服务（待接入）。

## 2.5 数据、记忆与个性化

**数据流（全本机）**：用户输入 → state（`data/user_state.json`）→ 组装提示词（阶段提示词 + 已知画像 + 参考/检索结果 + 历史 + 本轮输入）→ **发送至 DeepSeek API** → 回复与判定写回 state。

| 数据/制品 | 来源 | 用途 | 敏感性 | 处理方与传输 | 保留/删除 |
|---|---|---|---|---|---|
| 用户输入/提交产出 | 用户本人 | 澄清/判分/验收 | 中低（个人学习记录） | **传输至 DeepSeek API**；本机留存 | `/reset`、`/reset all`、删除 `data/` |
| 阶段提示词与阈值 | 本项目 | 驱动行为与规则 | 非敏感 | 随调用传输 | 代码版本管理 |
| 检索片段（启用后） | 外部网页 | 计划辅助 | 公开内容；**视为数据而非指令** | 注入提示词 | 不落地为索引 |
| 模型输出 | API | 教学/计划/判定 | 可能含错误 | 本机 state | 覆盖写入 |
| 日志/评测样本 | 待建（S-07） | 质量监控 | 含学习记录 | **本机 `data/metrics/`** | 待定 |

**记忆（模块 D）与用户控制：**

| 类型 | 写入依据 | 存放 | 更新 | 更正/删除 | 污染恢复 |
|---|---|---|---|---|---|
| 会话状态（四字段） | 仅采纳用户明说内容，**不推测** | 本机 JSON，单用户独占 | 增量合并，**空值不覆盖** | `/reset`、`coach/storage/reset.py` | 备份（5 份）可恢复 |
| 长期画像 | 测评判定 + 验收结论（**代码聚合**） | 同上 | 新知识点直接写入；已有取**新旧平均**平滑；薄弱点 <0.6 | 同上 + 重做任务 | 重置画像 |
| 对话历史 | 每轮追加 | 同上 | **现为全量保留并全量注入 → 待改为阶段隔离 + 窗口 8 条 + 归档（S-09）** | `/reset` | 归档可回溯 |

**用户是否知道并可控制个性化**：部分——可见画像与薄弱点、可清空/重置；但**尚无个性化开关**，记忆策略改动**待实现**。

**数据越界风险**：① 学习内容随调用传输第三方（**DeepSeek 数据条款待核**）；② 全量历史注入扩大暴露面与成本；③ 未来检索内容被误当指令（见 3.4 X-10/X-11）。

## 2.7 工具与 Agent 编排（模块 C）

| 动作/工具 | 用途与输入输出 | 执行主体与权限 | 只读/可写 | 确认点 | 超时/重试/幂等 | 回滚/审计 |
|---|---|---|---|---|---|---|
| 联网检索（待实现） | 补充外部信息；输入=查询，输出=结果+来源 | **由代码决定何时调用**（不由模型自由决定） | 只读 | 无需确认 | 需设**调用上限**与超时；失败降级（待定） | 丢弃结果即可；记 `tool_calls` |

**编排方式**：**混合（以固定路径为主）**。中断恢复：状态机阶段 + 守卫，中断后由 state 恢复。

## 3.1 成功指标与实验

| 类型 | 指标及操作定义 | 基线/获取 | 目标与时间窗 | 数据来源 |
|---|---|---|---|---|
| **首要结果** | **单次学习完成率** = 完成的任务数 ÷ 发起的学习次数 | **待测**（自用） | **待定** | 采集（**已实现**：`coach/metrics/`）+ state；**按验收档位与领域分层** |
| 次要结果 | **分档验收通过率**（L1/L2/L3 各自）；**档位爬升率**（连续 L1 通过后升档的比例）；首次验收通过率；平均澄清轮数 | 同上 | 待定 | 同上 |
| **护栏** | 单轮 token 成本；P95 延迟；幻觉抽样率；**平均每轮 LLM 调用次数**（workflow 效率护栏） | 无基线，先测 | 不得高于基线；幻觉不得高于待定阈值 | 采集（字段见 3.5） |

> **指标口径变更说明（v0.11）**：首要指标由"**7 天滚动计划完成率**"改为"**单次学习完成率**"，以匹配碎片化定位。
> **注意**：完成率**上升不等于学习质量上升**——质量由**验收档位与一致率**（次要结果 + 3.2）保证。
> 因此读指标时必须**同时看档位分布**：只看完成率会奖励"把任务变小"，这正是**趣味化/游戏化最容易腐化的地方（I-9）**。

**分析方法**：自用先建基线（**按单次会话统计，而非 7 天窗口**）；再 3 位碎片化学习者小样本验证（**同一知识点须观察档位是否爬升**，只升不爬＝碎片化退化为浅尝）。**注意选择偏差与样本限制**（熟人、非随机、无对照）。
**判断时间点与决策**：待定。达标 → 扩展领域或加入 S-11 对比；未达标 → **先简化 workflow / 收窄范围**。
**因果假设（待验证）**："完成率提升"代表"碎片时间被有效利用"，**而非**"学习者已掌握"——后者需档位证据。
